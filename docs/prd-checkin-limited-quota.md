# 签到限时额度与钱包优化 PRD

## 文档信息

- 文档版本：v1.0
- 文档状态：待评审
- 创建日期：2026-08-08
- 涉及模块：签到、钱包、统一计费、异步任务、系统设置、国际化

## 一、项目背景

现有签到奖励会直接增加用户的永久额度 `quota`。用户获得奖励后，额度不会过期，也无法与充值、兑换码等永久额度区分。

本次需要增加一种“当日限时额度”签到奖励。管理员可以设置每天几点开放签到；用户签到后获得的限时额度只能在当天使用，并在系统时区的次日 `00:00` 自动失效。

钱包需要分别展示永久额度和限时额度。限时额度可以参与正常 API 消费，但不能改变、覆盖或转化现有永久额度。

## 二、产品目标

1. 支持管理员选择签到奖励进入永久额度或当日限时额度。
2. 支持管理员配置每日签到开放时间。
3. 保证限时额度在次日零点自动失效，无须依赖定时清理任务。
4. 钱包分别展示永久额度与限时额度。
5. API 消费时优先使用限时额度，再使用永久额度。
6. 正确处理预扣费、结算、退款、并发消费和异步任务。
7. 保持现有充值、兑换码、邀请奖励、订阅和永久额度语义不变。

## 三、核心产品规则

### 3.1 签到开放时间

管理员配置 `08:00` 的含义是：

- 每天在系统时区的 `08:00` 开放签到。
- 用户可以在 `08:00` 至当天结束前签到。
- 并非只能在 `08:00` 这一分钟签到。
- 次日 `00:00` 后进入新签到周期，需要等待新一天的开放时间。

首期只配置开放时间，不配置单独的关闭时间。签到关闭时间固定为当天结束。

### 3.2 时区

- 所有签到日期、开放时间和失效时间使用服务启动时区，即环境变量 `TZ` 对应的系统时区。
- 后端时间判断是唯一权威来源。
- 前端不得使用浏览器本地日期自行判断是否为“今天”或是否已经开放。
- 管理员界面和用户界面需要展示实际使用的时区。

### 3.3 奖励类型

签到支持两种奖励类型：

- `permanent`：永久额度，维持现有行为。
- `temporary`：当日限时额度，不增加永久余额。

系统升级后的默认值为 `permanent`，避免改变已有站点的签到行为。

固定奖励和随机奖励继续复用现有额度配置，不为限时模式建立第二套金额配置。

### 3.4 限时额度有效期

- 限时额度从签到成功时开始可用。
- 失效时间固定为系统时区的次日 `00:00:00`。
- 用户在 `23:50` 签到，额度只能使用到当天结束。
- 配置变更不修改已经发放额度的失效时间。
- 关闭签到功能不应提前取消已经发放且仍有效的限时额度。
- 过期记录可以保留用于审计，但其剩余额度不再计入可用额度。

### 3.5 与永久额度的关系

- `users.quota` 始终表示永久额度。
- 签到限时额度不得写入 `users.quota`。
- 钱包不得将限时额度合并后覆盖永久余额的展示值。
- 充值、兑换码、管理员加款和邀请奖励继续只改变永久额度。
- `used_quota` 继续统计实际 API 总消费，不区分消费资金来源。

### 3.6 使用范围

限时额度可以用于：

- 普通同步 API 请求。
- 实时、流式请求。
- 图片、音频、视频等正常中继计费。
- 异步任务预扣费和最终结算。

限时额度不能用于：

- 购买订阅。
- 用户间额度转移。
- 提现或兑换。
- 转换为永久额度。
- 跨日结转。
- 增加 API Key 自身的独立额度。

### 3.7 扣费优先级

限时额度是“钱包”内部的子资金来源，不改变现有订阅偏好。

```text
选择钱包计费
    ↓
扣除有效限时额度
    ↓
限时额度不足时扣除永久额度
```

现有计费偏好保持如下语义：

- `subscription_first`：先使用订阅；回退钱包后，钱包内部先限时、再永久。
- `wallet_first`：钱包内部先限时、再永久；钱包整体不足时回退订阅。
- `wallet_only`：使用限时额度和永久额度，不使用订阅。
- `subscription_only`：只使用订阅，不使用限时额度和永久额度。

首期不支持“限时额度永远优先于订阅”。否则需要在单次请求中混合订阅和钱包两类资金来源，会显著扩大计费改造范围。

### 3.8 退款与失效

每次钱包消费必须记录限时额度和永久额度的实际扣费拆分。

- 请求失败且额度未过期：按原资金来源退款。
- 实际消费小于预扣费：优先退永久额度，再退限时额度。
- 实际消费大于预扣费：继续按当前有效限时额度优先的规则补扣。
- 退款发生在限时额度过期后：限时部分不得恢复为可用额度。
- 过期的限时额度不得退款到永久余额。
- 异步任务跨越午夜后失败，限时部分直接失效，只退回永久额度部分。

存在有效限时额度时，不使用钱包“信任额度免预扣”旁路，避免请求在零点前开始、零点后结算时失去明确的资金来源。

## 四、用户场景

### 4.1 管理员配置限时签到

1. 管理员进入“系统设置 → 计费设置 → 签到奖励”。
2. 开启签到功能。
3. 选择“当日限时额度”。
4. 设置每天 `08:00` 开放。
5. 设置固定奖励或随机奖励范围。
6. 保存后，新配置立即生效。

### 4.2 用户在开放前访问

- 签到卡显示“今日 08:00 开放”。
- 签到按钮禁用。
- 到达开放时间后，页面自动刷新为可签到状态。
- 即使用户绕过前端直接调用接口，后端仍拒绝签到。

### 4.3 用户签到并消费

1. 用户签到获得限时额度。
2. 永久余额保持不变。
3. 钱包显示本次限时额度和失效时间。
4. 用户发起 API 请求时优先扣除限时额度。
5. 限时额度不足的部分从永久余额扣除。

### 4.4 用户跨午夜停留在页面

- 到达失效时间后，签到页和钱包页自动刷新。
- 限时额度显示为零或已失效。
- 永久余额不发生变化。
- 新一天在配置的开放时间到达前不可签到。

## 五、功能需求

### 5.1 管理员签到设置

新增配置：

- `checkin_setting.reward_type`
- `checkin_setting.available_from_minutes`

字段定义：

- `reward_type`：`permanent` 或 `temporary`，默认 `permanent`。
- `available_from_minutes`：当天第几分钟开放，范围 `0` 至 `1439`，默认 `0`。

管理员界面要求：

- 奖励类型使用分段选择控件。
- 开放时间使用时间输入控件，界面显示为 `HH:mm`。
- 展示系统时区。
- 限时模式下显示“不会增加永久余额，午夜自动失效”的说明。
- 启用签到时，实际奖励必须大于零。
- 随机模式下最大值必须大于或等于最小值。
- 所有额度必须是非负整数且不超过 `common.MaxQuota`。
- 整组签到配置需要一次性校验并原子保存，避免逐项保存形成无效中间状态。

### 5.2 签到状态接口

`GET /api/user/checkin` 保留现有字段，并增加：

```json
{
  "reward_type": "temporary",
  "available_from_minutes": 480,
  "timezone": "Asia/Shanghai",
  "current_date": "2026-08-08",
  "server_time": 1786150000,
  "state": "not_open",
  "available_from": 1786156800,
  "expires_at": 1786204800,
  "next_transition_at": 1786156800,
  "temporary_quota": 0
}
```

`state` 支持：

- `not_open`
- `available`
- `checked`

前端使用 `state` 控制按钮，不通过错误字符串判断开放状态。

### 5.3 执行签到接口

`POST /api/user/checkin` 成功响应保留 `quota_awarded` 和 `checkin_date`，并增加：

```json
{
  "quota_awarded": 10000,
  "checkin_date": "2026-08-08",
  "quota_type": "temporary",
  "temporary_quota": 10000,
  "temporary_quota_expires_at": 1786204800
}
```

接口必须处理：

- 签到功能关闭。
- 尚未到开放时间。
- 当天已经签到。
- 奖励配置无效。
- 并发重复签到。
- 用户不存在或额度写入失败。

签到记录创建和奖励发放必须在同一数据库事务中完成。

### 5.4 钱包数据

钱包所使用的用户数据增加：

```json
{
  "quota": 500000,
  "temporary_quota": 10000,
  "temporary_quota_expires_at": 1786204800
}
```

约束：

- `quota` 保持永久额度原语义。
- `temporary_quota` 只返回当前仍有效的剩余额度。
- 已过期额度按零返回。
- 钱包数据不依赖签到功能当前是否开启。

### 5.5 钱包界面

钱包顶部显示四项：

1. 永久余额。
2. 今日限时额度。
3. 累计使用量。
4. API 请求数。

界面要求：

- 桌面端四列。
- 移动端 `2×2`。
- 限时额度单独显示失效时间和时区。
- 永久余额不得包含限时额度。
- 页面跨越午夜时自动刷新。
- 长文案允许换行，不截断关键信息。

### 5.6 签到界面

- 开放前显示开放时间，按钮禁用。
- 可签到时显示“立即签到”。
- 已签到时显示奖励额度和失效时间。
- 使用后端返回的 `current_date` 标识今天。
- 使用 `next_transition_at` 在开放时间或午夜自动刷新。
- 限时模式下替换现有“奖励直接加入余额”的说明。
- 签到成功提示使用完整插值文案，避免多语言字符串拼接。
- 日历星期名称使用本地化格式。

## 六、数据设计

扩展 `checkins` 表：

- `quota_type`：奖励类型，旧记录空值按 `permanent` 处理。
- `quota_remaining`：限时额度剩余量。
- `quota_expires_at`：限时额度失效时间，Unix 秒。
- `quota_awarded`：继续记录原始奖励总额。

设计原则：

- 当前需求只有签到产生限时额度，直接使用签到记录作为额度桶。
- 不创建午夜清零任务，查询和扣费时通过 `quota_expires_at` 判断有效性。
- 限时额度不进入永久额度 Redis 缓存。
- 扣减时在事务中读取有效签到记录，并通过 `lockForUpdate(tx)` 锁定。
- SQLite 使用同一事务流程，但共享锁定帮助函数会跳过不支持的 `FOR UPDATE`。

如果后续需要优惠券、活动赠送、管理员赠送等多种限时额度，应再抽象为通用限时额度账本。

## 七、计费设计要求

钱包资金来源需要保存本次消费拆分：

- 限时额度扣除量。
- 永久额度扣除量。
- 对应签到记录 ID。
- 限时额度失效时间。

需要覆盖的计费入口：

- 统一 `BillingSession` 预扣费。
- `WalletFunding` 结算和退款。
- 实时请求计费。
- 旧版 `PostConsumeQuota` 兼容路径。
- Midjourney 等直接余额检查路径。
- 异步任务差额结算。
- 异步任务失败原子退款。

不得把永久额度与限时额度直接合并写入 `relayInfo.UserQuota`，否则会改变：

- 动态倍率余额判断。
- 永久余额不足通知。
- 管理端余额含义。
- Redis 永久额度缓存语义。

应增加独立的钱包可用额度和扣费拆分字段。

消费日志的 `other` 增加：

- `temporary_quota_consumed`
- `wallet_quota_consumed`
- `temporary_quota_checkin_id`

现有日志总 `quota` 和 `billing_source=wallet` 保持兼容。

## 八、异步任务要求

任务私有数据需要持久化：

- 限时额度消费量。
- 永久额度消费量。
- 限时额度签到记录 ID。
- 限时额度失效时间。

必须改造：

- 任务提交后的资金来源快照。
- 任务最终额度重算。
- 任务补扣和部分退款。
- 任务失败原子退款。
- 任务跨午夜完成或失败。

异步任务退款时，不得把已经过期的限时额度写入永久余额。

## 九、兼容性要求

- 默认奖励类型为永久额度。
- 旧签到记录按永久奖励处理。
- 原有 `quota`、`used_quota` 字段语义不变。
- 现有签到 API 字段继续保留。
- SQLite、MySQL 5.7.8+、PostgreSQL 9.6+ 必须同时支持。
- 不使用数据库特定日期函数。
- 不改变订阅购买、充值、兑换码和邀请奖励行为。

## 十、国际化要求

新增用户文案必须覆盖：

- `en`
- `zh`
- `zh-TW`
- `fr`
- `ja`
- `ru`
- `vi`

建议新增文案：

- Check-in reward type
- Permanent balance
- Today's limited-time quota
- Check-in opening time
- Check-in opens at {{time}}
- Available from {{time}} until midnight
- Expires at {{time}}
- Not open yet
- Check in to claim today's limited-time quota
- This quota expires at midnight and does not increase your permanent balance.
- Check-in successful! Received {{quota}} in limited-time quota

语言文件必须通过 `add-missing-keys.mjs` 写入，并执行 `bun run i18n:sync`，不得直接编辑 locale JSON。

## 十一、验收标准

### 11.1 配置验收

- 管理员可以选择永久或限时奖励。
- 管理员可以配置每日开放时间。
- 无效时间和超大额度无法保存。
- 配置保存后立即生效。

### 11.2 签到验收

- 开放时间前无法签到。
- 开放时间整点可以签到。
- 当天只能签到一次。
- 限时签到不会增加永久余额。
- `23:59` 签到后额度在次日 `00:00` 失效。
- 前端时区与系统时区不同时，状态仍然正确。

### 11.3 计费验收

- 限时额度优先于永久额度。
- 支持限时和永久混合扣费。
- 总可用额度不足时拒绝请求。
- 预扣、补扣、部分退款和失败退款正确。
- 过期退款不会产生永久额度。
- 四种订阅计费偏好保持原行为。
- 并发请求不会重复消费同一限时额度。

### 11.4 钱包验收

- 永久额度与限时额度独立展示。
- 永久余额数值与改造前一致。
- 钱包展示准确失效时间和时区。
- 午夜后自动刷新为零。
- 桌面端和移动端无文字或布局溢出。

### 11.5 异步任务验收

- 异步任务可以使用限时额度。
- 差额结算保留正确的资金拆分。
- 跨午夜失败时不会恢复过期限时额度。
- 任务退款不会把限时额度转成永久余额。

## 十二、开发任务拆分

### TASK-01：签到配置与校验

目标：增加奖励类型和每日开放时间配置。

工作内容：

- 扩展 `CheckinSetting`。
- 增加 `reward_type` 和 `available_from_minutes`。
- 增加额度上限、奖励类型和开放时间校验。
- 增加签到配置整体保存接口，使用批量原子更新。
- 保持默认值兼容现有行为。

依赖：无。

### TASK-02：签到时间领域逻辑

目标：统一签到日期、开放时间和失效时间计算。

工作内容：

- 使用 `common.NowInStartupTimezone()`。
- 计算当天开放时间和次日零点。
- 输出 `current_date`、`state` 和 `next_transition_at`。
- 覆盖夏令时和跨午夜边界。

依赖：TASK-01。

### TASK-03：签到限时额度数据迁移

目标：为签到记录增加限时额度余额和失效信息。

工作内容：

- 扩展签到模型。
- 更新普通迁移和快速迁移。
- 兼容历史签到数据。
- 验证三种数据库迁移。

依赖：无。

### TASK-04：签到发放事务

目标：保证签到记录和奖励发放原子完成。

工作内容：

- 永久模式继续增加永久额度。
- 限时模式写入签到额度桶，不修改永久额度。
- 使用唯一索引防止并发重复签到。
- 统一三种数据库的事务和回滚行为。

依赖：TASK-01、TASK-02、TASK-03。

### TASK-05：钱包限时额度模型接口

目标：提供有效限时额度查询和钱包余额快照。

工作内容：

- 查询当前有效限时额度。
- 过期额度按零处理。
- 返回永久额度、限时额度和失效时间。
- 不改变现有永久额度缓存结构。

依赖：TASK-03。

### TASK-06：统一钱包扣费改造

目标：实现限时额度优先、永久额度补足。

工作内容：

- 扩展 `WalletFunding`。
- 事务内锁定限时额度记录。
- 保存预扣资金拆分。
- 支持补扣、部分退款和完整退款。
- 存在有效限时额度时禁用信任额度旁路。
- 保持动态倍率只使用永久余额。

依赖：TASK-05。

### TASK-07：兼容计费路径治理

目标：确保所有钱包消费入口都能使用限时额度。

工作内容：

- 检查实时请求计费。
- 检查 `PostConsumeQuota` 兼容路径。
- 检查 Midjourney 直接余额检查。
- 检查图片、音频、视频和任务入口。
- 消除绕过统一钱包资金来源的限时额度消费路径。

## 十四、完成定义

满足以下条件后，本功能才可以交付：

- 管理员能够配置奖励类型和每日开放时间。
- 开放前后签到状态由后端正确控制。
- 限时签到不会修改永久余额。
- 所有钱包计费路径能够优先消费限时额度。
- 预扣费、结算、同步退款和异步退款能够保留资金拆分。
- 午夜后限时额度不可继续使用，也不会转换为永久余额。
- 钱包能够独立展示永久额度和限时额度。
- 七种语言完整。
- 后端边界测试、前端行为测试、类型检查、Lint 和生产构建通过。
- 桌面端和移动端完成实际页面验收。
